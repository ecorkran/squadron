1. [x] **(901) Pipeline Code-Review Diff Injection and UNKNOWN-Fails-Closed**
Fixes [issue #11](https://github.com/ecorkran/squadron/issues/11): pipeline
code reviews silently produce UNKNOWN/no-findings because the diff is never
injected into the review prompt. Three coordinated changes:

1. Forward `slice` explicitly from phase / review step `expand()` into the
   review action config (deterministic key, not merged-params side channel).
2. Replace per-template `match` in `_resolve_slice_inputs` with a declarative
   template-input registry, so any template that declares it consumes a
   diff gets one resolved automatically.
3. Treat verdict `UNKNOWN` as `FAIL` for `on-fail` checkpoint triggers (fail
   closed) so dead reviewers and parser misses can't silently wave through.

7. [x] **(909) Pipeline Phase-Step Correctness — Dispatch Post-Condition + Review Frontmatter Project + Review-Code Scope Guard**
Fixes [issue #15](https://github.com/ecorkran/squadron/issues/15), [issue #16](https://github.com/ecorkran/squadron/issues/16), and [issue #17](https://github.com/ecorkran/squadron/issues/17). Three independent pipeline/CLI correctness bugs, all surfaced during slice 303 planning, bundled into one maintenance slice because each is small and all three sit on the phase-step / review command correctness path.

**Part A — Dispatch artifact post-condition (#15, Medium).** A phase-step `dispatch` expected to *write an artifact* (design doc, task file) returns `success=True` whenever the agent's turn completes, with no check that the file was created. An agent that stops mid-task to ask a question — or never writes the file — is indistinguishable from success; the failure surfaces one step later at the review action with a misleading "prior step may not have created the expected file" message. Two coupled sub-problems: (1) dispatch has no artifact post-condition — the phase step knows the expected output (a `tasks` phase expects a task file) so the check likely belongs there, not in generic dispatch; (2) an unattended agent that ends its turn with a question has no answer path — it should route to a checkpoint/escalation rather than complete silently. Repro: `sq run p5a 303` (`run-20260707-p5a-73bbffc0.json`). (Ruled out CF review gates — squadron reads no `review_gate` setting.)

**Part B — Review frontmatter hardcodes `project: squadron` (#16, Low).** `format_review_markdown` (`persistence.py:119`) emits `project: squadron` as a string literal on every review file, in every project — a review run in context-forge is mislabeled `squadron`. `ProjectInfo` (`context_forge.py:52`) does not currently carry the project name; the fix adds it (from the `cf get --json` response already parsed in `get_project`), threads it via `SliceInfo`/`resolve_slice_info` (which already calls `get_project()`), and replaces the literal — falling back to a non-silent `unknown`, never `squadron`. Verify both write paths (pipeline `actions/review.py:201`, CLI `persistence.py:268`) per interface-parity.

**Part C — `sq review code` silently runs unscoped review when slice index missing/malformed (#17, Medium).** `review_code()` (`cli/commands/review.py:604-607`) declares `slice_number` as a fully optional Typer argument with no fallback validation; when it's omitted (or consumed by a misparsed flag), execution falls through with no `diff`/`files`/`slice_info` and no error. `_run_review_command`'s required-inputs check (`review.py:302-308`) is a no-op because the `code` template declares `required_inputs: []`. `code_review_prompt()` (`review/builders/code.py:40-44`) then substitutes an unconstrained "survey the project structure" instruction, and that prompt is sent to a real LLM, producing a confident, fully-formed review citing plausible-but-nonexistent files — a silent hallucinated-output failure, not a crash. Fix: require at least one of `slice_number` / `--diff` / `--files` before proceeding, mirroring the existing hard guards in `review_slice`/`review_tasks` (`review.py:408-410`, `551-553`). Repro: `sq review code -v --model glm51` run from context-forge with no slice index — produced a CONCERNS verdict citing files (`src/document-resolver.ts`, `src/git.ts`, etc.) that don't exist in that repo.

**Slice design:** `user/slices/909-slice.pipeline-phase-step-correctness.md`
**Task file:** `user/tasks/909-tasks.pipeline-phase-step-correctness.md`
**Status:** complete (20260710) · **Risk:** Medium (Part A) / Low (Part B) / Medium (Part C) · **Effort:** 4/5 · **Dependencies:** [149]

8. [x] **(910) Loop Convergence Correctness — Findings Feedback + Multi-Review Gate + Dry-Run Expansion**
Fixes [issue #42](https://github.com/ecorkran/squadron/issues/42), [issue #43](https://github.com/ecorkran/squadron/issues/43), and [issue #45](https://github.com/ecorkran/squadron/issues/45). Three defects on the multi-step `loop:` path, bundled because Parts A and B share a single 60-line function (`_execute_loop_body`) and one test file. Together #42 and #43 make "the loop fixes the findings and re-reviews" false for the demo pipeline. Each part is small because the machinery already exists — this is wiring, not new architecture. [Issue #44](https://github.com/ecorkran/squadron/issues/44) was scoped here initially and split out to slice 911, which follows this one.

**Target loop shape.** These fixes assume — and Part B enforces — one dispatch plus one review per loop body, with sequential loops for multi-phase work. The motivating pipeline is an app-creation flow: concept, then architecture review until pass, then per slice `design → review until pass`, `task breakdown → review until pass`, `implementation → code review until pass`. Every loop in that sketch is one-dispatch-one-review, which is what makes `_resolve_prompt_from_prior_review`'s "most recent REVIEW" lookup unambiguous. **Sequential phase gating — verified present, one hole (20260731).** That pipeline depends on a failed loop blocking the next step, so this was checked before scoping. It works for two of the three `on_exhaust` modes: the pipeline run loop returns on `FAILED` (`executor.py:881`) and on `PAUSED` (`executor.py:873`), so `on_exhaust: fail` and `on_exhaust: checkpoint` both stop the run and the next phase never starts. **`on_exhaust: skip` returns `SKIPPED`, which appears nowhere in the run loop and falls through** — a design loop that exhausts under `skip` lets the task-breakdown loop run against the failed design, exactly the waste Part B's reasoning rules out. Latent, not active: nothing ships using it (`judge-cycle.yaml` uses `checkpoint`, `test-loop.yaml` uses `fail`), and the app-pipeline above works today provided each loop uses `fail` or `checkpoint`. Arguably `skip` means "keep going" by definition — but there is currently no way to express "this phase is optional" as distinct from "this phase failed and everything downstream is now meaningless," and the mode name does not warn you. **Decision deferred**, and out of scope for all three parts below: none of them change this behavior. Resolve separately as either a guard, a rename, or documented intent.

**Part A — Loop retries do not feed findings back into the re-run (#42, High).** `_execute_loop_body` (`pipeline/executor.py:1298-1321`) passes the *outer* `prior_outputs` into every `_execute_step_once` call (line 1308) and never updates it; `iteration_action_results` is reset at the top of each round (line 1299) and discarded. Iteration N+1 therefore re-runs a prompt identical to iteration N's — the loop re-rolls the same dice rather than converging. The consumer is already built and correct: `DispatchAction._resolve_prompt_from_prior_review` (`actions/dispatch.py:258`) walks `context.prior_outputs` in reverse for a `REVIEW` result, formats findings into a fix prompt, and already handles the empty-findings case — it is simply never fed. Fix: accumulate each inner step's results into a per-iteration `prior_outputs` copy and pass that down, mirroring the `dict(prior_outputs)` snapshot pattern `_execute_step_once` already uses (`executor.py:1030`). Effort 1/5 for the edit. **Verify during design:** how `step_outputs` interacts with `prior_outputs` inside `_execute_step_once` — the fix touches exactly that boundary and it is the one place a hidden complication could raise the estimate.

**Part B — `until:` silently gates on one review when a body contains several (#43, High).** `_last_with_verdict` (`executor.py:356-360`) returns the first verdict found walking backward, so in a body containing several reviews only the final one gates `until:` — a design review that FAILs while a tasks review PASSes exits the loop successfully.

**Fix: reject the ambiguity, do not resolve it.** A loop body with more than one verdict-bearing action and an `until:` condition should fail at validation time with an actionable message, not pick one silently. All-verdicts-must-pass was considered and rejected: the correct decomposition is one dispatch + one review per loop, with sequential loops for multi-phase work (design until pass, *then* task breakdown until pass, *then* implementation until code review passes). Task breakdown against a failed design is wasted work, so a gate that runs every phase and then reports a composite verdict solves a problem that should not exist. Gating on all reviews would convert a silent wrong answer into a correct-but-wasteful one. The two-loop structure in `p45b.yaml` is therefore the recommended pattern, not a workaround for this defect.

This narrows the part considerably — no semantics decision, no change to `evaluate_condition` (`executor.py:334`), which stays correct for the one-review-per-body shape both loop paths now assume. Sequence first: it establishes the loop shape Part A's tests assert against. Effort 1/5.

**Part C — `sq run --dry-run` does not expand loop bodies (#45, Low).** A `loop:` step prints as a single opaque line (`loop-0 (loop)`), omitting the body's steps and the `max` / `until` / `on_exhaust` configuration — so the construct with the most surprising execution shape and the highest cost when wrong is the one `--dry-run` describes least. Parsing is already correct (`--validate` reports the pipeline valid), making this a display gap only. Independent of Parts A and B: shares no code, can land in any order. Effort 1/5.

**Slice design:** `user/slices/910-slice.loop-convergence-correctness.md`
Branch: `910-slice.loop-convergence-correctness`, close issues #42/#43/#45 on merge.

**Status:** complete (20260731) · **Risk:** Medium (Parts A/B) / Low (Part C) · **Effort:** 2/5 · **Dependencies:** none

9. [x] **(911) Loop Iteration Versioning and Review Evidence** — complete 20260801
Fixes [issue #44](https://github.com/ecorkran/squadron/issues/44) and two adjacent problems it does not record. Split out of 910 during scoping because these are document-contract and evidence-integrity questions rather than loop-execution ones: 910 makes an iteration *converge*, this slice makes an iteration *legible* — recoverable and identifiable. Sequenced immediately after 910, not deferred: 910's Part A closes the findings-feedback gap, and until this slice lands there is still no way to prove from the artifacts that it worked. A fourth part (review-note carry-forward) was scoped here and split out to slice 912 during design, per the note below.

**Part A — Commits between iterations (#44, Medium).** Each iteration overwrites the previous artifact with no commit in between, so a converging loop leaves nothing to diff round-over-round and no way to recover a better earlier attempt. Diagnostically coupled to 910's Part A: without per-round history there is no evidence the fed-back findings were actually addressed, and a byte-identical round — an empty commit — is precisely the symptom 910 Part A fixes. A `commit` step type already exists, so the machinery is present. Open: whether the loop inserts a commit automatically or it belongs in the body as an explicit step; every-round vs. only-on-change; message format; and whether this is opt-in (`commit_each_iteration: true`) so existing loops do not begin writing history unexpectedly. Mechanical once decided. Effort 2/5.

**Part B — No version indicator on the artifact (Low).** Not recorded in #44. Open a slice design document and nothing indicates whether it is round 1 or round 3, or which verdict it last survived — the artifact is not self-describing. Proposed: a simple integer `version: {n}` in frontmatter, deliberately not semver; iteration count is a counter, not a compatibility contract. Squadron writes frontmatter routinely (confirmed with the user, 20260731), so the mechanism exists and this is small. Effort 1/5.

**Part C — Overwrite vs. modify, and what survives a round (Medium).** A contract decision rather than an implementation one: is each iteration a clean regeneration with the version tag as the only carryover, or does content persist and accumulate across rounds? Simplest-that-works favors clean regeneration, and simplest is usually right for a contract other tools read. **Note the seam:** artifact frontmatter is the documented boundary with Context Forge review-gating, so adding a field is a cross-tool contract change, not a squadron-local one — coordinate before settling the schema. Also needs a migration answer for artifacts written before the field existed (absent `version` must mean something explicit, not be silently treated as round 1). Effort 2/5.

**Part D — split out to slice 912 (20260731).** The original fourth part — do review notes carry forward, and may a reviewer see the prior version — was carved out during Phase 4 design, on the plan's own instruction to split rather than expand. It is the prerequisite consumer of this slice's output, not part of it. See entry 10.

**Field name (20260731).** Part B above proposes a "version indicator." The field is named **`revision_number`**, not `version` — the latter invites a semver misreading, and `revision` alone still allows the value to be treated as a label rather than a count. The slice design carries a full field contract (who writes it, what absent means, which docTypes, and that nothing may branch on its value).

**Design correction (20260731).** Part A above states that "a `commit` step type already exists." It does not: `commit` is an *action* emitted only by phase-step expansion, and is not a registered step type, so it cannot appear as a bare step in a loop body. Consequence, verified during design: a loop whose body is phase steps (`p45b.yaml`) already commits once per iteration — the gap there is that every round's message is identical — while a loop whose body is a bare `dispatch:` (`judge-cycle.yaml`, `test-loop.yaml`) commits nothing. The slice design carries the corrected account.

**Slice design:** `user/slices/911-slice.loop-iteration-versioning-and-review-evidence.md`
**Status:** complete · **Risk:** Low (Part C) / Medium (Parts A/B) · **Effort:** 2/5 · **Dependencies:** [910 (Part A defines what an iteration produces and feeds back), 909 (Part A's artifact post-condition is the hook Part B stamps from)]

11. [x] **(913) Ruff Rule-Set Adoption — `B`, `ASYNC`, `BLE`**
Closes the first three steps of [issue #50](https://github.com/ecorkran/squadron/issues/50). The Python guide (`.claude/rules/python.md`) requires `select = ["E", "F", "W", "I", "UP", "BLE", "ASYNC", "B"]`; the project selects `["E", "F", "W", "I", "UP"]`. Raised as F009 in the slice 305 code review, where `W` was enabled (zero violations) and the rest deferred rather than folded into a review-fix branch.

The point is not lint hygiene. `BLE` and `ASYNC` are named in the guide as the *mechanical enforcement* for two rules the project otherwise states only in prose — the exception-handling policy and event-loop discipline. Unenforced, those rules are aspirational, which is how [issue #49](https://github.com/ecorkran/squadron/issues/49) landed: a bare `except` in `cf_op` silently dropping `--embed` for non-SDK models.

**Part A — `B` (70 violations, mostly mechanical).** 13 of the 70 are `B008` on `typer.Option`/`typer.Argument` in CLI signature defaults — the standard Typer idiom, not debt. Those want one `per-file-ignores` entry for `src/squadron/cli/commands/`, not 13 rewrites; do that first, then the remaining 54 `B904` (`raise ... from err`) and three stragglers (`B007`, `B017`, `B905`) are a single mechanical pass with no behavior change. Effort 1/5.

**Part B — `ASYNC` (6 violations).** Four `ASYNC221` (blocking `subprocess.run` inside async functions) are in tests. The two that matter are `ASYNC240` — blocking `pathlib` calls in async functions, one of them in `src/squadron/client/http.py:42`, on a production I/O path. Small, but a real fix rather than an annotation. Effort 1/5.

**Part C — `BLE` (23 violations, all in `src`).** The substantive part. Every site is a decision, not a mechanical edit: narrow the exception type, or keep the broad catch with the justifying comment and explicit `# noqa: BLE001` the guide requires. Expect a few to surface genuinely swallowed errors the way #49 did — that is the return on this slice, and the reason it is worth more than the other two parts combined. Sites cluster in `pipeline/` (executor, prompt_renderer, state, loader, sdk_session, three actions), the CLI commands, and the two provider agents. Effort 2/5.

Sequence A → B → C: A is noise reduction that makes C's diff readable. Deliberately excludes pyright-over-tests (entry 12), which is a sweep of a different character and should not interleave with these.

**Counts re-measured during design (20260815).** The figures above were taken when issue #50 was filed and have drifted; the slice design carries the current numbers and they supersede these. Two drifts changed the design rather than just the arithmetic: (1) `B904` is a **CLI-shaped** problem — 53 of 54 sites are in `src/squadron/cli/commands/` (25 in `run.py` alone), with one straggler in `pipeline/emit.py`, so Part A is a single-directory pass rather than the codebase-wide sweep described above; and (2) `BLE` is **28, not 23** — the 23 in `src` are as stated, but five more live in the tracked `project-documents/user/reference/codebase-probe.py`, which CI lints today because `ruff check` runs with no path argument. 12. [ ] **(914) Strict Type Checking Over the Test Suite**
Closes the fourth step of [issue #50](https://github.com/ecorkran/squadron/issues/50). `[tool.pyright] include = ["src"]`; the guide specifies `["src", "tests"]`, on the rationale that bugs in tests mask bugs in code. Widening the include reports **868 errors across 234 test files** under `typeCheckingMode = "strict"` — volume rather than difficulty, concentrated in untyped fixtures, `MagicMock` returns, and unannotated helper signatures.

Worth doing on evidence, not principle: slice 305's F001 was a severity-case mismatch that survived a full slice because every test fixture hand-wrote the finding dict instead of routing through the production path, and nothing type-checked the difference. Strict typing over tests would not have caught that specific string-value bug, but the class of drift it belongs to — fixtures that no longer resemble what production emits — is exactly what typed fixtures make visible.

**Slice design:** `user/slices/914-slice.strict-type-checking-over-the-test-suite.md` — resolves all three open questions on measured evidence. Re-measured at `03cdd73`: **905 errors across 104 files**, not 234 — the 234 was files *analyzed*, not files erroring. 14. [x] **(916) Review Scope Correctness — Diff Resolution, Empty-Scope Verdicts, and Tool Jail Roots**
Fixes [issue #89](https://github.com/ecorkran/squadron/issues/89), [issue #62](https://github.com/ecorkran/squadron/issues/62), [issue #70](https://github.com/ecorkran/squadron/issues/70), [issue #86](https://github.com/ecorkran/squadron/issues/86), and [issue #69](https://github.com/ecorkran/squadron/issues/69); likely closes [issue #71](https://github.com/ecorkran/squadron/issues/71). Five defects answering one question: **did the review examine the change set the operator meant, and was it equipped to read it?** Bundled because all five sit on the `sq review` CLI entry path (`cli/commands/review.py`) plus `review/git_utils.py`, and because #89 and #62 were observed on the *same* live PR review — the wrong subject and the empty subject are the two halves of one credibility failure.

Motivating context: squadron reviews are moving toward PR-centric use against enterprise repos, where a branch is routinely a few merges behind its base. Every defect here fires under exactly those conditions.

**Part A — `--diff <ref>` uses a two-dot diff (#89, High).** [issue #32](https://github.com/ecorkran/squadron/issues/32)'s fix (`6f5af84`) added merge-base resolution to `resolve_slice_diff_range`, which runs only on the automatic slice-number path — [review.py:849-852](src/squadron/cli/commands/review.py#L849-L852) calls it *only when `--diff` is absent*. An explicit `--diff origin/main` passes through untouched to `extract_diff_paths` ([rules.py:202](src/squadron/review/rules.py#L202), a literal `git diff --name-only <ref>`) and into the prompt. Any branch behind its base is then reported as *reverting* whatever the base gained since the fork point. Observed live on a private GHE repo: a confident top-line FAIL claiming the PR reverted session-lifetime and SSO fixes it does not touch — confirmed against GitHub's own merge-base file list. Fix: route `--diff` through `resolve_diff_base()` / merge-base resolution. Decide whether a literal two-dot comparison remains reachable behind a separate flag, or is dropped.

**Part B — empty filtered scope reports PASS (#62, High).** When `diff_exclude_patterns` ([code.yaml](src/squadron/data/templates/code.yaml)) filters every changed file out of the range, the reviewer correctly reports that nothing was in scope — at severity `note`, which leaves `verdict: PASS`. Observed clearing a review gate on slice 362 with zero lines examined. Not markdown-specific: any all-`.toml`/`.json`/`.csv` range does the same.

**Decision (20260910): refuse to persist and exit non-zero. No new `Verdict` member.** The alternative — a `NOT_APPLICABLE` / `NO_SCOPE` verdict — was rejected on two grounds.

First, it models the event wrongly. A verdict says "a review happened and this was its answer"; here nothing was reviewed. That is an input error of the same kind as Part C (no scope supplied) and [issue #17](https://github.com/ecorkran/squadron/issues/17) (scope missing entirely), and it earns the same treatment Part C establishes: no artifact, non-zero exit, and a message naming the exclusion patterns that emptied the range.

Second, squadron's three verdict-consuming gates are **allowlists of named verdicts, not exhaustive switches**, so a new member is silently mishandled in three different directions rather than caught: `CheckpointTrigger.ON_CONCERNS` ([checkpoint.py:22](src/squadron/pipeline/actions/checkpoint.py#L22), `{CONCERNS, FAIL, UNKNOWN}`) would not trip and would wave it through; `LoopCondition.REVIEW_CONCERNS_OR_BETTER` ([executor.py:249-252](src/squadron/pipeline/executor.py#L249-L252), `{PASS, CONCERNS}`) would never be satisfied and the loop would not converge; `_aggregate_verdicts`' `rank` dict ([review.py:333](src/squadron/cli/commands/review.py#L333)) does a bare subscript and would raise `KeyError`. Two more consumers assume the closed set — `_LEG_VERDICT_TO_RESOLUTION` ([resolution.py:70-72](src/squadron/review/resolution.py#L70-L72)) and the `degraded` computation at [persistence.py:198](src/squadron/review/persistence.py#L198). And because `workflow.review_threshold` has **no consumer in squadron** (review gating lives in Context Forge — the seam is the frontmatter contract), a new member is additionally a cross-repo contract change.

Refusing to persist fixes the reported harm directly: the artifact that cleared a gate on slice 362 carried `verdict: PASS`, and no artifact clears no gate, in either repo, with no coordination.

**Accepted consequence:** a pipeline whose slice is genuinely all-docs now fails rather than passing. That is the true and visible outcome, and it makes an existing convention load-bearing instead of optional — per #62's own scope note, a slice whose substantive change is documentation or a skill prompt is covered by design and task reviews with the code review set to `none`. **Confirmed during design (20260910):** omission is expressible today and needs no new work — `PhaseStepType.expand` emits the review action only when the `review:` key is present ([phase.py:76](src/squadron/pipeline/steps/phase.py#L76)), so dropping the key suppresses both the review and its checkpoint. **Part A — verdict frontmatter is unvalidated against the enum (#77, Medium).** Nothing checks a review artifact's `verdict:` key against `Verdict` ([models.py:10-16](src/squadron/review/models.py#L10-L16): PASS, CONCERNS, FAIL, UNKNOWN). 16. [x] **(918) Review Grounding — Reading the Right Text and Recording Why Output Was Lost**
Fixes [issue #94](https://github.com/ecorkran/squadron/issues/94) and [issue #92](https://github.com/ecorkran/squadron/issues/92), and folds in the destructive-delete half of [issue #65](https://github.com/ecorkran/squadron/issues/65). Where 916 asks whether the review examined the right *scope* and 917 asks whether the persisted artifact can be *trusted*, this asks whether the reviewer read the **document actually under review** — and, when its output is lost anyway, whether the artifact records why. Parts A and B are one family: a review that grades text other than the file in front of it. Part C is unrelated and rides along because it is small, contained, and a data-loss bug.

**Part A — a re-review grades the prior revision, not the file under review (#94, High).** Observed on `sq review arch 380 -v` (minimax-m3, tools enabled), third consecutive run at `reviewedSha: bd306bc8`. The saved review quoted three phrases that had been *removed* from the document in the two prior revisions and repeated the corresponding findings as unaddressed, while the current file states each point explicitly. The third run escalated to **FAIL on recycled findings**. This defeats the review gate loop outright: a re-review after a disposition cannot be trusted to grade the revised document, so the loop cannot converge.

Verified mechanism (20260913): **no prior-review context is injected anywhere** — no builder and no template references a prior review, so injection is ruled out as the source and the issue's third suggested check needs no work. The stale text reached the model through the tool jail. `archive_existing_review` ([persistence.py:439](src/squadron/review/persistence.py#L439)) writes every superseded review to `<reviews>/archive/` under its original name, and the jail root for a document review is the repo root — so the archived predecessors of the very document under review sit inside the jail, named to match it, and the model found them. The run also cited `user/analysis/942-analysis.tech-debt-audit.md`, confirming it was reading around the tree.

The fix is a **jail deny-list**, and the seam already exists: every read, list, and grep passes through `resolve_in_jail` ([_shared.py:26](src/squadron/tools/builtin/_shared.py#L26)) or `contained_in_jail` ([_shared.py:43](src/squadron/tools/builtin/_shared.py#L43)) — verified as the universal chokepoint across `file_tools.py`, `search_tools.py`, and `bash_tool.py`. Neither helper has any exclusion concept today; containment is the only predicate. Add one: a second question (*is this a path this review type may read?*) returning `None` on the same code path as a containment failure, so every existing caller's handling works unchanged — no new error path and no change to any tool contract. Follow `contained_in_jail`'s established D6 precedent: **silent to the model, WARNING to the operator** — a model told "you were denied" will probe the boundary, and an excluded path must be indistinguishable from one that did not match.

**Decisions (20260913, PM): exclude the whole reviews directory, and scope the exclusion per review type.**

*Broad, not narrow.* Excluding only `reviews/archive/` fixes the observation and leaves the bug. The live review of the document under review is the most on-topic file in the tree for that reviewer, and on the third run it held findings the author had already dispositioned — the recycled-findings failure reproduces from the live file alone. Observed layout for the reported case: one live `380-review.arch.pull-request-workflow.md` plus five archived predecessors, every one of them name-prefixed with the document under review.

The tension is real and was weighed: a re-review arguably *should* know what the last round said, so it can judge whether findings were addressed. It is resolved by *discovered* vs. *injected*, not by yes/no. 305's findings-addressed gate already passes prior findings deliberately — a known set, from a known revision, labeled as prior. #94 is that same information arriving by accident: unlabeled, from an arbitrary mix of revisions, indistinguishable from the document being graded. A model cannot tell "raised and since fixed" from "wrong now," and on run three it chose FAIL. Broad exclusion closes the discovery path; 305 keeps the injection path, where labeling and revision-scoping already live.

*Per review type, not global.* Code reviews read the tree broadly by design — that is how a finding cites a real file — and their scope is a diff, so archived reviews are not name-adjacent to what they examine. Document reviews (arch, slice, tasks) examine one named document, and reviews are never part of what they grade. A global switch would either break code reviews or leave document reviews exposed. The exclusion applies to document review types only.

17. [x] **(919) Verification That Verified Nothing — Newline-Free Parsing, Verdict Provenance, and a Fail-Closed Frontmatter Gate**
Fixes [issue #96](https://github.com/ecorkran/squadron/issues/96), [issue #97](https://github.com/ecorkran/squadron/issues/97), and [issue #98](https://github.com/ecorkran/squadron/issues/98). One theme across three layers: **a check that verified nothing must not report success.** 916 asked whether the review examined the right scope, 917 whether the artifact can be trusted, 918 whether the reviewer read the right document. This asks whether a *pass* means anything — a parser that found no structure still publishes a verdict, a derived verdict is indistinguishable from a stated one, and a validator that checked zero files still satisfies its gate. Parts A and B are one family and share `parsers.py` and `ReviewResult`; Part C is the same bug class one layer out, in the commit gate, and is independent code.

**Part A — a newline-free response loses its verdict and collapses four findings into one (#96, High).** Observed on `sq review slice 918 -v --model kimi27` (openrouter `moonshotai/kimi-k2.7-code`), 20 tool calls at sha `4b04eece`. The model returned a complete, well-formed review — `## Summary`, verdict `PASS`, four findings (three PASS, one NOTE), each with its own `category:` and `location:`. The persisted artifact carries **one** finding whose summary is a 1300-character run-on containing all four findings' text, and `location: unverified`.

The provider delivered 3076 characters with **zero** `\n`. Assembly is not at fault: `review_client.py` joins parts with `"\n".join` (the #22 fix) and this was a single part. Three parser constructs then failed for one reason — each requires a literal newline the markdown structure does not actually depend on. `_SUMMARY_RE` ([parsers.py:69](src/squadron/review/parsers.py#L69)) requires `##\s+Summary\s*\n+` before the verdict keyword, so `_extract_verdict` returned UNKNOWN with `## Summary` present and `PASS` immediately after it. `_FINDING_RE` ([parsers.py:80](src/squadron/review/parsers.py#L80)) terminates each finding on a lookahead whose every alternative is `\n`-anchored, so only `\Z` could match and finding #1 absorbed the other three. `_CATEGORY_RE` / `_LOCATION_RE` ([parsers.py:105-106](src/squadron/review/parsers.py#L105-L106)) are `^…$` under `re.MULTILINE`, so zero of the four `category:`/`location:` pairs were extracted. Restoring newlines to the same text takes finding matches from **1 to 4**.

This is a squadron bug, not a model-formatting complaint. `CLAUDE.md`, "Parsing & Pattern Matching": *a regex that silently fails on valid input (e.g. requiring exact whitespace counts or line-ending positions) is a bug; parse the semantic content, not the formatting.* The output was semantically complete.

**The real design risk is 917 Part F, and it is verified, not hypothetical.** The fence-masking that closed #91 — a model's fenced restatement of the required format being parsed as findings — is line-anchored by construction: `_FENCE_OPENER` is `^[ \t]*(fence)` under `re.MULTILINE` ([parsers.py:488](src/squadron/review/parsers.py#L488)), and `_mask_fences` ([parsers.py:498](src/squadron/review/parsers.py#L498)) preserves offsets by blanking fence interiors. Section bounding to `## Findings` assumes line structure the same way. So leniency cannot be added to the three constructs in isolation: a newline-free document has no line structure for the masker to find, and making headings match mid-line without a compensating story reopens #91 on any response that quotes the format inline. Whether fences are even recoverable from newline-free text needs deciding before implementation, not during it.

Design questions to settle: does leniency apply always, or only on a document detected as newline-free (a narrower blast radius, at the cost of two parsing modes to maintain)? A normalization pass that reinserts breaks before `##`/`###`/tag boundaries and then runs the existing parser unchanged is one shape worth weighing against relaxing each regex in place — it keeps one parser and one set of line-structure assumptions, but it rewrites model text before parsing, which the artifact must then disclose.

At minimum, **a response containing zero newlines is itself a diagnosable condition** and must be reported rather than silently mis-parsed. 918 Part B already added the newline-free indicator to the Run Digest, so the reporting seam exists; this part decides what the parser does about it.

**Part B — a derived verdict is indistinguishable from a stated one (#97, High).** Independent of A: any parse failure that still yields at least one finding publishes a verdict that looks stated and is not. The #96 run wrote `verdict: PASS` into frontmatter and it was committed. Nothing parsed it — `_extract_verdict` returned UNKNOWN, the collapsed single finding happened to carry `pass` severity, and `_verdict_from_findings` ([parsers.py:122](src/squadron/review/parsers.py#L122)) derived PASS by most-severe-wins over it.

The recovery itself is correct and deliberate (#28); its docstring says it exists "only to recover a verdict the summary parse lost." The defect is that **the recovery does not reach the surface the gates read.** 917 added a COMMIT action validating `verdict:` against the `Verdict` enum — it checks the value is *legal*, not that it was *found*, and `PASS` is a legal member.

Verified (20260913), and this narrows the work to one asymmetry: `fallback_used` is already set exactly when a verdict is derived after a failed summary parse ([parsers.py:802](src/squadron/review/parsers.py#L802), [:829](src/squadron/review/parsers.py#L829)), already serialized into `to_dict()` ([models.py:201](src/squadron/review/models.py#L201)), and already consumed in the artifact *body* — `persistence.py:405` renders the "findings not parsed" section from it, and `:340` folds it into `degraded`. But `_review_frontmatter_lines` ([persistence.py:242](src/squadron/review/persistence.py#L242)) takes no degradation parameter of any kind and emits no such key. Context Forge's review gate reads **frontmatter**. So a derived PASS auto-clears CF's gate, CF cannot tell it from a stated PASS, and the same run's JSON says `fallback_used: true`. The information exists and is already computed; it just does not reach the consumer. Amoeba reports the identical false-negative in its own routing (it auto-continues on PASS), and CF initiative 240 gates on verdict.

A derived PASS is strictly worse than a derived FAIL, and the bias is structural: `_verdict_from_findings` returns PASS unless it sees FAIL or CONCERN, so *any* parse failure that drops or mangles the severe findings while leaving a benign one yields a clean pass. That is exactly the shape #96 produced.

Two implementation caveats from the issue, both verified: `fallback_used` stays `False` in the nothing-parsed-at-all branch ([parsers.py:816](src/squadron/review/parsers.py#L816), deliberately commented) — that path leaves `verdict: UNKNOWN` and is self-announcing, needing nothing extra. And `fallback_used` does not distinguish *why* the parse failed: #96's newline-free shape and an ordinary reshaped summary both set it.

**Open decision for the PM before task breakdown:** a frontmatter key (e.g. `verdictSource: stated | derived`) is greppable and lets each gate choose its own policy — CF could treat `derived` as not-clearing without squadron dictating it — but it is a schema addition needing a context-forge coordination step like slice 383's. A `ReviewResult`-and-digest-only change is cheaper and needs no coordination, but remains unreadable to any external gate and helps only a human who opens the file. The consumer evidence above argues for the frontmatter key; whether this slice also carries the boolean or a reason string is the second half of that call. 917's verdict gate is the natural place to enforce whichever policy is chosen.

**Part C — the frontmatter gate cannot fail in a git worktree (#98, Medium).** `frontmatter_gate.py:44` invokes `cf validate frontmatter` with explicit staged paths. cf validates "only the in-root .md files among them (others are silently skipped)", and in-root resolves against the registered project Identity path — the default checkout. Explicit paths under a sibling worktree are dropped silently with exit 0. Reproduced from two checkouts with the same throwaway file: default checkout `filesChecked: 1`; sibling worktree `filesChecked: 0`, exit 0. Confirmed on a real tracked document in the worktree too.

The gate reads only the exit code and never asks how many files were checked, so it cannot distinguish "validated and passed" from "validated nothing." In any non-default worktree it reports `squadron.frontmatter-gate: ok` having verified nothing, byte-identical to a real pass. A gate whose purpose is to fail closed on bad frontmatter currently fails **open**, in an environment squadron itself encourages — the project uses cf worktree contexts and `git worktree` for parallel slice work, and initiative 380 is running in one right now.

The signal exists and is ignored: `cf validate frontmatter --json` reports `filesChecked` (verified available on the installed cf — `-j, --json`, output `{"filesChecked": 1, "totalFindings": 0, ...}`). Read it, and treat `filesChecked == 0` against a non-empty staged-path list as a failure whose message names the likely cause, since the operator cannot infer it from cf's silence. Same fail-closed reasoning 917 applied to the verdict gate for unreadable frontmatter, and it holds whether or not cf lands its fix.

Root cause is [context-forge#88](https://github.com/ecorkran/context-forge/issues/88) and squadron cannot fix that — but a validator reporting success having checked nothing should never satisfy a gate, so the defense belongs here regardless of cf's timeline. Note the gate must not become brittle against a cf build that omits `filesChecked`: an unreadable or absent count is itself an indeterminate result and takes the same fail-closed path.

**Scope notes, verified:** `squadron.review-verdict-gate` is unaffected — it reads and parses each staged path itself ([review_verdict_gate.py:97](src/squadron/events/actions/review_verdict_gate.py#L97)) and never shells out to cf. The default checkout is unaffected, so this is not a regression in single-checkout use. Also related: [context-forge#87](https://github.com/ecorkran/context-forge/issues/87), the presentation half of the same worktree-root inconsistency.

**Not scoped here.** [#92](https://github.com/ecorkran/squadron/issues/92) / [#99](https://github.com/ecorkran/squadron/issues/99) ride along as **evidence only**. 918 Part B landed the stop-reason instrumentation and the reproduction did not reproduce across two runs, so no branch of the mechanism is selected. D7's rule from 918 holds: do not fix a mechanism speculatively. #99 records what to read out of the digest when it recurs; leave both open. [#90](https://github.com/ecorkran/squadron/issues/90) (artifact naming for slice-less reviews) is adjacent to the review-artifact surface but is a naming *design* decision with collision and discoverability consequences, and its silent-failure half is already closed by 916 Part C — it stays in Future Slices.

Sequence **A → B → C**, revised from C → A → B during slice design. A must precede B: A removes the trigger that produced the derived verdict, and settling A's leniency story tells B how many distinct degradation shapes the provenance flag has to describe. B carries the only cross-repo dependency, so starting it after A leaves the most room for the context-forge coordination to resolve. C is self-contained — it touches no review-parsing file and needs no coordination, so it can land at any point; ordering it first would only delay A, the highest-severity defect and the one whose design decision the other parts depend on.

18. [ ] **(920) Claude Agent SDK Upgrade — 0.1.38 → 0.2.x and Retiring the Rate-Limit Parser Shim**
Fixes [issue #30](https://github.com/ecorkran/squadron/issues/30). The pin is `claude-agent-sdk>=0.1.38`; the installed version is 0.1.38 and the current release is **0.2.152** (the issue was filed against 0.2.128 and the gap has widened since). The bundled CLI ships with the package and has moved ahead of the pinned parser, so the CLI emits message types the parser treats as fatal — the observed symptom was a real `sq metrology audit run` dying mid-stream after ~30 tool calls with `ProviderError: Unknown message type: rate_limit_event` from the parser's `case _:` fallthrough.

**The compatibility surface was probed before scoping, not assumed.** Installing 0.2.152 in a throwaway venv and exercising it against squadron's actual usage: all 14 public names squadron imports are present (`AssistantMessage`, `ClaudeSDKClient`, `ClaudeAgentOptions`, `ResultMessage`, `SystemMessage`, `TextBlock`, `ToolUseBlock`, `ToolResultBlock`, `query`, and the five error types); all 9 `ClaudeAgentOptions` fields squadron sets (`cwd`, `permission_mode`, `system_prompt`, `model`, `tools`, `allowed_tools`, `setting_sources`, `hooks`, `max_turns`) still exist, and both option shapes squadron constructs build without error; and the three private modules squadron reaches into — `_internal.message_parser`, `_internal.client`, `_errors` — all still exist with the same shape, including the module-scope `parse_message` binding on `_internal.client` that the shim patches separately. So #30's framing of "~90 releases of drift touching every provider path" overstates the risk: the drift is real, but the API squadron depends on held across the minor bump.

**What actually changes is the rate-limit path.** 0.2.152 parses `rate_limit_event` natively, returning a **new** `RateLimitEvent` message type (it is now in `query()`'s return union alongside `StreamEvent` and `ConversationResetMessage`). That makes [`install_rate_limit_parser_shim`](src/squadron/providers/sdk/rate_limit.py) dead by its own terms — its docstring says *"Remove once the pin moves past a parser with native support"*, and the wrapper only ever sees payloads the real parser rejected, so it silently becomes a no-op rather than failing loudly. But the retirement is not a deletion: throttle detection is currently keyed off a **parse failure** (`MessageParseError` carrying a payload, classified by `rate_limit_event_blocks`), and that failure will no longer occur. A `rejected` status must still reach the backoff path, which now means recognizing a typed event instead of a caught exception. Getting this wrong fails silently in the direction that matters — squadron would stop backing off under genuine throttling and hammer the rate limiter, which is the exact defect the backoff was added to fix.

Two further consequences follow from `RateLimitEvent` being a new type. Message-type dispatch in [`translation.py`](src/squadron/providers/sdk/translation.py) and the agent's `_skip_unparseable` path will both encounter something they have never seen; the defensive skip (`97c3cb3`) is correct to keep regardless of version, but it must not become the thing that swallows `rejected`. And `ClaudeSDKClient` gained methods squadron does not use (`set_model`, `get_context_usage`, `stop_task`, `rewind_files`, MCP controls) — out of scope here, but `set_model` is worth noting because the pipeline's model-override path currently works around its absence.

**Proposed shape — three parts.** **A:** raise the pin to a tested floor and decide pin-vs-range, retire the shim, and confirm `_skip_unparseable` still guards only genuinely-unknown types. **B:** route `RateLimitEvent` through translation and re-key throttle classification off the typed event rather than `MessageParseError`, preserving the `allowed`/`allowed_warning`/`rejected` distinction and the existing backoff schedule — `rate_limit_event_blocks`'s classification logic survives, its input changes. **C:** verification per the issue's own acceptance bar — the full provider suite, plus at least one real end-to-end review and one metrology audit, since the original failure appeared only in a long-running audit after ~30 tool calls and no unit test would have caught it.

**Open question for design:** whether the shim is deleted outright or kept as a version-guarded no-op for users pinned below the new floor. Deleting is cleaner and the floor makes it unreachable; keeping it hedges against a user with a stale lockfile, at the cost of carrying code that cannot be exercised. Decide in slice design, not during implementation.

**Status:** not started · **Risk:** Medium (touches every SDK-backed path — review, dispatch, pipeline, metrology — and the failure mode of getting the rate-limit re-keying wrong is silent: no backoff under real throttling, observable only as degraded behavior under load) · **Effort:** 3/5 · **Dependencies:** none — the compatibility probe found no blocking API breakage, so this can be picked up independently
