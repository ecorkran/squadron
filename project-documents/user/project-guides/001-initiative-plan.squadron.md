# Initiative Plan: Squadron

## Source
Retroactively generated from existing architecture documents.

## Index Convention
Variable gaps based on initiative scope. Working range 100-799 for feature initiatives, 900+ reserved for cross-cutting maintenance and refactoring.

## Initiatives

1. [x] **(100) Orchestration (Python Reboot)** — Core engine, agent providers, CLI interface, review system, daemon. M1 shipped (v0.2.7). Dependencies: None (foundation). Status: in_progress
2. [x] **(140) Pipeline Foundation** — Action protocol, declarative pipeline definitions (YAML), executor with step sequencing, model resolution cascade, basic and collection loops, state persistence and resume, built-in pipelines (slice-lifecycle, review-only, design-batch). Ships `sq run` as a working replacement for run-slice. Dependencies: [100]. Status: draft
3. [ ] **(180) Pipeline Intelligence** — Weighted review convergence strategies (decay-based finding dismissal), model pools with selection strategies, escalation behaviors (auto-retry with stronger model), conversation persistence across retries, findings ledger with cross-iteration identity matching. Layers sophistication onto 140's foundation. Dependencies: [100, 140]. Status: draft
4. [ ] **(200) Multi-Agent Communication** — Shared message bus, configurable routing topologies, supervisor with health monitoring and restart strategies, multi-provider agent coordination, human-in-the-loop participation. Dependencies: [100]. Status: not_started
5. [ ] **(220) Simulation Runtime** — Persistent agent entities with identity and emergent behavior in shared environments. Future work. Dependencies: [100, 200]. Status: future_work
6. [ ] **(240) Pipeline Auth-Boundary Flexibility** — Decouple pipeline execution from unconditional Claude SDK auth. Two SDK-touching paths (persistent `SDKExecutionSession` for cross-step Claude dispatches; one-shot `ClaudeSDKAgent` spawned by the provider registry for review/dispatch when a Claude profile is resolved) become independently controlled. Per-step auth classification via pre-scan of resolved models, conditional persistent-session creation (connect iff some step actually needs it), profile-aware dispatch routing in pure-CLI executor mode, and clear error semantics when pool resolution mid-run conflicts with the upfront classification. Goal: pipelines composed entirely of non-Claude profiles run end-to-end without Claude auth, login, or account; mixed pipelines pay Claude cost only where actually used; persistent-session lifetime guarantees (compact/rotate-only termination) preserved for SDK-profile dispatch chains. Explicit non-goals: until-loop convergence intelligence, fan-out/fan-in aggregation semantics, intra-loop compaction policy, conversation-vs-override-instruction routing for review findings — all 180-band. One-shot Claude subprocess pooling/reuse documented as known cost, not optimised here. Dependencies: [100, 140]. Status: not_started.
7. [ ] **(260) Non-SDK Agent Tool Use (OpenAI-Compatible Agentic Loop)** — Add tool-calling capability to non-SDK provider agents (openrouter, openai, local, gemini) so dispatch and review actions can use models like Kimi-K2.5, GPT-4-class, etc. for tasks that require file I/O. Today the `OpenAICompatibleAgent` is text-in/text-out only: it detects tool calls in the streaming response but never passes a `tools` parameter to the API and never executes them, so capable models emit raw tool-call XML into the response stream and pipeline steps that depend on file writes (e.g. `design`) silently fail. This initiative implements an agentic loop inside `handle_message`: pass a tool schema to the API, execute returned `tool_calls` via squadron-side tool implementations (file read, file write, bash sandboxed to CWD), accumulate the assistant/tool-result message history within the call, and re-invoke the model until it returns a response with no `tool_calls`. Tool access is controlled by an explicit `allowed_tools` allowlist on `AgentConfig` (empty by default) — the project rejects "all tools by default" for non-SDK models. Implementation is structured for future lift-out: the loop lives in a private `_run_agentic_loop` method so when the higher-level orchestration layer (tentatively planned) needs to observe intermediate tool calls, the boundary is already extracted. Goal: pipelines using capable non-SDK models (Kimi, GPT-4, etc.) for design/dispatch steps actually produce file artifacts; allowed_tools is enforced; max-iteration guard prevents runaway loops. Explicit non-goals: streaming intermediate tool calls to the executor (deferred to orchestration initiative), MCP tool bridging beyond context-forge (separate slice if pursued), changes to the SDK path (which already has full tool support via Claude Code preset), `review`/`summary` action coverage (initial scope is `dispatch` only). Dependencies: [100, 140, 240]. Status: not_started.
8. [ ] **(280) Shared Agent Artifact Store** — SQLite-backed persistent store for structured artifacts written by agents during pipeline execution. Enables multi-model, multi-agent pipelines where agents (Codex implementer, Claude reviewer, minimax summarizer) coordinate through durable content entries rather than through the orchestrator or real-time message passing. Each agent appends typed artifacts (`implementation_summary`, `review_findings`, `task_progress`, `checkpoint`, `devlog`) that downstream steps can inject into their prompts via template variables. Primary motivation: `CodexAgent` produces filesystem side effects but no structured output — a shared store lets it record what it did so a subsequent reviewer can read it. Secondary: cross-run continuity for long implementations, operator observability via `sq artifacts list`. Architecture: `280-arch.shared-agent-artifact-store.md`. Dependencies: [100, 140, 260]. Status: not_started
9. [x] **(300) Intrinsic LLM Judging & Scoring** — Add non-human intelligence at squadron's pipeline decision points. Squadron is an excellent deterministic workflow engine running a non-deterministic process; its automation breaks at the *decision points* (e.g. "is this slice-design good enough to proceed, or escalate to a human?"), which is why human-in-loop is still required at too many gates — heavy enough that simple projects aren't worth the overhead. This initiative lets an LLM render a *scored judgment* on an artifact against its **in-repo ground truth** (parent doc, project rules, codebase, phase success-criteria — no external answer key) so the engine can gate on that judgment automatically and bubble only the hard calls up to the human. Two reuse-first capabilities: **(1) a numeric 0–100 score** added additively to the review/action result models, parser, and persistence (the keystone slice, done first and alone), with the verdict *derived from* the score by a configurable threshold (score is source of truth; verdict is its projection for the existing `--step-done --verdict` machinery) and an optional `criteria` map reserved from the start so a future per-criterion breakdown is not a second migration; **(2) an intrinsic judge** = the **existing `review` action** with a judge system-prompt that emits score+findings, composing with the **existing** `each`/`loop`/`commit` steps to run the review→fix→re-review cycle unattended. Prioritize the design-phase gates (slice-design vs. arch, tasks vs. slice) where human-in-loop is heaviest. Explicit non-goals: a new `eval:judge` action (rejected as duplicative of `review`); any agentic/turn-loop inside the engine (judges are one-shot like reviews; tool-using orchestration is the far-future orchestrator, above the engine); reference-dataset eval (a separate product — curated input/expected pairs to grade a model in the abstract — a poor fit here given non-deterministic outputs and weak top-of-hierarchy ground truth). Architecture: `300-arch.eval-actions-llm-as-judge-scoring.md`. Dependencies: [100, 140]. Status: complete.
10. [ ] **(320) Judge Calibration & Quality Metrology** — Answer "how much can I trust these judges?" and "is model X an overreacher while Y rubber-stamps?" by measuring judge quality against a human-sampled oracle, and establish a measurable code-quality baseline. Builds on 300's judges existing. The ground truth for judge quality is **the human, sampled** — the operator spot-checks a sample of judge verdicts and the system reports judge-vs-human agreement and judge-vs-judge dispersion (no curated dataset). Trust is not uniform: it scales with in-repo ground-truth strength (high for tasks-vs-slice, low for arch-concept-vs-initiative-blurb), so calibration is *per artifact level* and feeds 300's escalate-vs-auto-gate decision. Also includes a **code-quality oracle**: a tech-debt-audit analysis (forked MIT Claude skill, adapted for squadron projects) run across projects to capture a baseline, plus a dispatch-side **prompt-chaining pre-emption** prompt that front-loads avoidance of the issues the audit finds — the first measurable customer of the metrology (audit-findings-per-project should drop). Two oracles, same metrology shape: tech-debt-audit for code quality, human-sampled agreement for design quality. Dependencies: [100, 140, 300]. Status: not_started.
11. [x] **(340) Skill Pack Infrastructure** — A thin, opt-in extension mechanism that lets users install curated sets of external Claude Code skills (slash commands) alongside squadron's first-party commands. Addresses squadron's growing use in analysis of existing codebases, where purpose-built external skills (tech-debt-audit, understand-anything, etc.) provide value that first-party commands don't cover. Core design: a TOML manifest (`skills.toml`, per-user or per-project) lists named skill packs with an external source (local path or git ref); `sq skills install <pack>` copies the pack's command markdown into `~/.claude/commands/<prefix>/`, exactly mirroring how `install-commands` works today; `sq skills list` shows installed vs. available packs. A shipped `analysis` pack (opt-in) bundles the forked tech-debt-audit skill and similar analysis tools as its first customer. Open design question resolved via a planned spike: whether packs are invoked via a dispatch file (`/sq:analysis <skill>`) or a dedicated command prefix (`/analysis:<skill>`) — the spike determines which pattern Claude Code handles reliably. No MCP, no plugin registry, no dynamic discovery — the unit of capability is a markdown file in `~/.claude/commands/`. Dependencies: [100]. 

12. [x] **(900) Maintenance and Refactoring** — Cross-cutting maintenance, tech debt, refactoring, and operational improvements that span initiative boundaries. Dependencies: None. Status: not_started

## Cross-Initiative Dependencies
- 140 depends on 100: needs stable agent dispatch, review system, model aliases, CF integration layer, and CLI interfaces
- 180 depends on 100, 140: builds on 140's action protocol, pipeline executor, model resolver, and structured review findings
- 200 depends on 100: builds on agent registry, provider protocols, and daemon infrastructure
- 220 depends on 100, 200: requires both core engine and multi-agent communication layer
- 240 depends on 100, 140: builds on agent registry / provider-profile resolution (100), the pipeline executor and model resolver (140), and the persistent `SDKExecutionSession` lifecycle established in 140. Coordinates with 180 at the auth-classification ↔ pool-resolution boundary but does not depend on 180.
- 260 depends on 100, 140, 240: builds on the agent registry and `OpenAICompatibleAgent` (100), the dispatch action and `AgentConfig` interface (140), and the profile-aware dispatch routing established in 240. Independent of 180.
- 280 depends on 100, 140, 260: needs the agent registry and pipeline executor (100, 140), and coordinates with the tool registry from 260 for the `write_artifact` tool call path. Independent of 180 and 200.
- 300 depends on 100, 140: reuses the agent registry / provider-profile resolution and the template-parameterized review engine `run_review_with_profile` (100), and the `review` action, executor, `each`/`loop`/`commit` steps, model resolver, and `--step-done --verdict` checkpoint machinery (140). A judge is a review template plus a numeric score — no new action and no engine execution-model change. The numeric-scoring keystone slice extends the `ReviewResult` / `ActionResult` models (100, 140) additively. Independent of 180, 200, 260, and 280; explicitly does not depend on 260's agentic loop (judges are one-shot).
- 320 depends on 100, 140, 300: needs 300's judges and numeric scores to exist before their trustworthiness can be measured. Reuses the review/judge result models and persistence (300) and the provider registry (100, 140) to run multiple judges for inter-judge agreement. The human-sampled oracle and the tech-debt-audit code-quality baseline are new to this initiative. Independent of 180, 200, 260, 280.
- 340 depends on 100: builds on the `install-commands` file-copy mechanism and CLI command registration (100). Independent of all other initiatives; 320 is a consumer (analysis pack is the first customer of the tech-debt-audit skill) but 340 does not depend on 320.
- 900 is independent: maintenance work applies across all initiatives as needed

## Future Work
- **Orchestrator / "organism"** — An agent intelligent enough to drive Context Forge + squadron and act reasonably on their outputs, conversing with and guided by the human only on the hard calls. This is the top rung of a determinism/leverage ladder: (1) today's high-accuracy/high-effort workflow engine, (2) judge-at-decision-points (initiatives 300/320) trading some accuracy for far less effort, (3) this orchestrator — adding an intelligence *above* the engine for another leverage jump. In the organism metaphor, the CF structures are the stable skeleton, the LLM judges/orchestrator are the nervous system (joints absorbing variability and making local decisions), and the human is consulted only where it matters. Architecturally critical point: this is the **only** place a true agentic perceive→decide→act loop belongs, and it sits *above* squadron consuming its CLI/JSON — **not** inside a pipeline action. Adding intelligence reduces determinism; the leverage is worth it at this layer, but the engine and its judges (300) must stay one-shot and deterministic. Far-term; named here to prevent its loop from being smuggled into 300-band components. Promote to a full initiative when pursued.
