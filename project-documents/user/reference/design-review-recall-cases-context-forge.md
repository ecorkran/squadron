# Design, architecture and task review recall: candidate cases, context-forge batch (self-verified, 2026-11-16)

Read-only pass over `/Users/manta/source/repos/manta/context-forge` using `git show`, `git diff`, `git log`, `git grep` at the reviewed commit. Nothing was checked out, no model was called, no `sq` command was run. 15 candidates examined (all of `batch-context-forge.json`: 2 arch, 5 slice designs, 8 task files). The stop rule did not trigger: the first 8 candidates produced 7 valid cases.

Validity rule applied (same as `design-review-recall-cases.md` and `design-review-recall-cases-3.md`): a flaw counts only if, in the text the reviewer saw (`<commit>` or `<commit>^`), the document contradicted itself, its parent, or code in the repo at that commit, left out something its own success criteria required, or held a task that could not be completed as written. It does not count if the correction follows a later decision, scope change, new gate or capability, filled-in unspecified detail, a style or size opinion, or facts that only existed after other slices were built. Borderline items are INVALID and tagged `borderline`.

Method: no later commit proves the flaws. The saved review's findings and the response diffs were leads only. Every valid flaw below was checked by me against the document at the reviewed commit and, where named, the code or sibling documents at that commit. A reviewer claim I could not verify is INVALID (unproven). Each valid flaw says whether the original review raised it; the original reviewer's model is the control for those.

Labels on evidence: every item below is **read** (I read the reviewed text and the code or sibling document named); none is **inferred**.

Flaw types: **doc** = needs only the reviewed document, its parent design or sibling documents; **code** = needs source code at the reviewed commit. Tag `coverage` marks a valid flaw of the form "the tests omit a branch its parent design's success criterion names" (softest valid type; drop them if only strong flaws are wanted).

1. **Reviewer saw a different text than the one I read** in 240-arch, 210-slice, 241-slice, 910-slice and 915-slice (`doc_at_review_commit` or `parent_of_response`). The text at the reviewed commit often already answers the review (240, 910, 915), so those reviews' own findings cannot be scored against it. For 268, 272 and 925 the file is added by the response commit and exists in one version only.
